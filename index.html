01 / WHY THIS EXISTS

A working node.
Still a white screen?

The node is not always the problem. When proxy software, TUN routing, and local app pages share one path, unclear traffic boundaries can stall the launch screen or break the language service connection.

01□

Local traffic takes the wrong route

localhost, 127.0.0.1, and ::1 should stay direct. Proxy settings can still affect them, causing white screens or timeouts.

LOCAL TRAFFIC / DIRECT
02↗

Proxy is only half-configured

Environment variables, system proxy settings, and local listening ports can disagree. The launcher reads candidates and tests whether an HTTP proxy is actually usable.

PROXY / VERIFY FIRST
03↻

Too much manual setup

No more hunting for install paths, toggling TUN, or trying ports. The launcher combines detection, verification, and startup in one action.

02 / HOW IT WORKS

Three steps to a cleaner launch.

This is not a proxy client and it does not take over your network settings. It prepares a clearer connection environment only for the process that starts Antigravity.exe.

03 / CLEAR SCOPE

NO TUN is the goal,
not an absolute promise.

When your local proxy core provides a usable HTTP(S) proxy, Antigravity can run without relying on TUN mode. The launcher does not disable, modify, or take over your TUN settings.

✓Included
  • Detect Antigravity.exe automatically
  • Find and verify a local HTTP(S) proxy
  • Keep a direct path for local addresses
  • Works with Windows PowerShell 5.1 and 7
  • Does not change system proxy or execution policy
—Not included
  • Antigravity CLI login
  • Account, password, or token management
  • Disabling or configuring your TUN mode
  • Turning a SOCKS5-only proxy into an HTTP proxy
  • Replacing Clash, Mihomo, or another proxy core
